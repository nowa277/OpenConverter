# Android KGG v5 解密支持设计

## 背景与问题

Android 端目前只实现了旧式 KGM/KGMA/VPR 掩码解密。新式 KGG v5 文件虽然仍使用 KGM 文件头，但需要根据文件头中的 `EncryptionKeyId` 从酷狗 `KGMusicV3.db` 取得逐文件密钥，再执行 QMC2 密钥解包和流解密。

现有转换流程还会按文件名最后一个扩展名判断输入类型。因此，`*.kgg.flac` 会被误判为普通 FLAC，未经解密便交给 FFmpeg，最终表现为 Android 转换失败；输出名也会错误地保留 `.kgg`。

## 已验证事实

- 原始测试目录包含 9 个 `*.kgg.flac` 文件，均为 KGG v5、V1 ekey、RC4 数据路径。
- Win10 酷狗客户端新下载的测试集包含 23 个 `.kgg`，覆盖 3 个专辑及标准、高品、Hi-Res 三档 KGG 音质。
- 同一首歌的无损版本为旧式 `.kgma`；补充专辑还包含旧式 `.kgm` 和明文 `.mp3`，可用于兼容性回归。
- 最新 `KGMusicV3.db` 包含 24 个 KGG 密钥。23 个 `.kgg` 使用独立实现解密后，均与 `unlock-music.dev/cli` 参考实现逐字节一致。
- 当前真实样本均为 V1/RC4；MAP 和 V2 分支将使用确定性的合成测试向量覆盖，不依赖难以定向获取的线上文件。
- 测试音频和用户数据库仅作为本地端到端测试材料，不进入 Git 历史。

## 目标

1. Android 可以导入酷狗 `KGMusicV3.db`，并使用其中的逐文件密钥解密 KGG v5。
2. `.kgg` 和复合扩展名（例如 `.kgg.flac`）都能被正确路由，不再按伪装的末尾扩展名当作明文音频。
3. 旧式 `.kgm`、`.kgma`、`.vpr` 和普通音频转换行为保持不变。
4. 缺少数据库、密钥不匹配或数据库无效时给出可操作的错误，而不是模糊的 FFmpeg 返回码。
5. JVM 算法测试和 Pixel 8 模拟器端到端测试均通过。

## 非目标

- 不在应用内寻找或破解未由用户提供的酷狗账号、数据库或密钥。
- 不提交受版权保护的音频、真实 `KGMusicV3.db` 或从中提取的密钥。
- 不改动桌面端无关流程，也不顺带重构现有转换架构。
- 不新增云端服务、网络密钥查询或账号登录功能。

## 方案选择

### 采用：Android 原生导入数据库并本地解密

设置页通过 Storage Access Framework 让用户选择 `KGMusicV3.db`。应用将加密数据库复制到应用私有目录，启动或导入时在私有临时文件中解密数据库、只读查询 KGG 密钥表并加载为内存映射，随后删除临时明文数据库。转换器按文件头的密钥 ID 查询映射并解密音频。

这是推荐方案，因为它完整覆盖用户的 Android 使用场景，不要求用户在电脑上预处理密钥文件，同时保持数据库和密钥只在本机应用沙箱内。

### 未采用：只导入预提取的 `kgg.key` 或 JSON

实现较少，但需要额外桌面工具和操作步骤，无法形成独立的 Android 端到端流程。

### 未采用：只识别 KGG 并返回“不支持”

可以修复误报，但不能完成解密目标。

## 架构与组件

### `KggDatabaseImporter`

- 接收 SAF 返回的 `ContentResolver` 输入流。
- 校验数据库基本结构和支持的加密格式。
- 将原始加密数据库原子复制到应用私有目录。
- 使用与参考实现一致的数据库页解密方式生成私有临时 SQLite 文件。
- 只读查询 `ShareFileItems`，产出 `EncryptionKeyId -> EncryptionKey` 映射。
- 在成功和失败路径都关闭 SQLite 句柄并删除明文临时文件。
- 只有完整导入成功后才替换上一份可用数据库，避免错误文件破坏现有配置。

### `KggKeyStore`

- 应用启动时从私有目录中已保存的加密数据库重建内存映射。
- 对解码器只暴露按密钥 ID 查询的窄接口，以及供设置页展示的密钥数量和导入状态。
- 不记录或展示真实密钥内容，不把明文密钥写入日志或 Git 测试资源。

### `KggV5Decoder`

- 校验 KGM 魔数、头长度、加密模式和密钥 ID 长度，拒绝截断或越界头部。
- 仅接管 KGG v5（加密模式 `5`）；旧式模式 `3` 继续交给现有 `KgmDecoder`。
- 通过 `KggKeyStore` 获取 ekey，按参考实现支持 QMC2 V1/V2 密钥解包，以及 MAP/RC4 两种数据路径。
- 以流式方式处理音频负载，避免把几十兆 Hi-Res 文件整体载入内存。
- 解密产物继续交由现有格式探测和 FFmpeg 转码流程处理。

### 转换路由

路由顺序调整为：

1. 读取足够的文件头，优先识别受支持的加密格式。
2. 若文件头是 KGG v5，调用 `KggV5Decoder`，不受末尾伪扩展名影响。
3. 若是旧式 KGM/KGMA/VPR，保持现有解码器路径。
4. 只有未识别为加密格式时，才按普通输入扩展名直接交给 FFmpeg。

输出名会剥离已识别的完整加密后缀：`song.kgg.flac` 和 `song.kgg` 均以 `song` 作为基础名；不会对普通文件名进行泛化清理。

### 设置页

设置页新增一个“KGG 密钥数据库”区块：

- “导入 KGMusicV3.db”按钮启动 SAF 文件选择器。
- 成功后显示已加载的密钥数量和导入成功状态。
- 失败时显示原因，但不显示数据库内部密钥。
- 不申请全盘存储权限；应用只读取用户明确选择的文档 URI。

## 数据流

### 数据库导入

`用户选择 URI -> 复制加密数据库到临时文件 -> 解密到私有临时 SQLite -> 校验并读取密钥 -> 原子替换保存的加密数据库 -> 更新内存映射 -> 删除明文临时文件`

### 文件转换

`选择音频 -> 文件头识别 KGG v5 -> 读取 EncryptionKeyId -> 内存映射查询 ekey -> 解包 QMC2 密钥 -> 流式解密 -> 格式探测 -> FFmpeg 转码 -> 写入目标目录`

## 错误处理

- 未导入数据库：提示“请先在设置中导入 KGMusicV3.db”。
- 文件密钥不存在：提示数据库与音频不匹配，并建议从下载该文件的酷狗环境重新导入最新数据库。
- 数据库格式或密码不受支持：导入失败并保留上一份可用数据库。
- KGG 文件头损坏：报告不合法或截断的 KGG 文件，不进入 FFmpeg。
- 解密后格式无法识别：报告解密产物格式未知，并保留诊断上下文但不记录密钥。
- 单文件失败继续遵循现有批量转换语义，不影响其他任务。

## 测试策略

### JVM 单元测试

- 数据库页解密：使用最小合成数据库或固定非敏感测试向量验证页头、分页和查询结果。
- ekey 解包：覆盖 V1、V2、MAP、RC4 以及无效 Base64/TEA 数据。
- KGG 文件头：覆盖有效模式 5、旧模式 3、截断头、非法长度和未知模式。
- 数据流解密：对不同偏移和分块大小验证输出一致，防止流式 RC4 偏移错误。
- 路由：证明 `.kgg.flac` 优先进入 KGG 解码，而普通 `.flac` 仍直通。
- 输出命名：覆盖 `.kgg`、`.kgg.flac`、`.kgma` 和普通多点文件名。
- 错误信息：覆盖未导入数据库和缺失密钥。

所有缺陷先由失败测试复现，再编写最小实现使其通过。

### 本地参考实现对照

- 使用 Win10 最新下载集和匹配数据库运行环境门控测试。
- 23 个 KGG v5 文件的原生解密结果必须与 `unlock-music.dev/cli` 逐字节一致。
- 真实样本不加入仓库，测试通过环境变量显式指定路径。

### Android Pixel 8 端到端

1. 构建并安装 debug APK 到现有 Pixel 8 模拟器。
2. 通过设置页真实导入最新 `KGMusicV3.db`。
3. 分别转换标准、高品、Hi-Res KGG，以及原始 `*.kgg.flac` 样本。
4. 回归转换旧式 `.kgm`、`.kgma` 和普通 MP3/FLAC。
5. 对输出运行 `ffprobe`，验证容器、时长可读和非零音频流；对无损中间解密结果与参考实现做哈希或逐字节对照。
6. 使用不匹配数据库验证缺失密钥提示。

## 仓库行为

- 工作从最新 `origin/main` 的独立分支 `fix/android-kgg-v5` 开始。
- 保留用户现有未跟踪文件，不将 `.codex/`、`upload_all.sh`、音频或数据库纳入提交。
- 设计、测试、实现和必要文档使用范围清晰的提交；每个变更行都直接服务于 KGG 修复或其验证。
- 完成前检查 Git diff、敏感数据、测试结果和 Android 端到端证据。

## 完成标准

- 新增单元测试先失败后通过，现有测试无回归。
- 真实 23 文件参考对照全部通过。
- Pixel 8 上至少完成 KGG 三档音质、复合扩展名、旧 KGM/KGMA 和普通音频的端到端验证。
- 错误数据库和缺失密钥路径显示可操作信息。
- Git 历史不包含测试音频、数据库、密钥或无关用户文件。
